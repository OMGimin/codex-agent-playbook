# 설계 배경

## 총괄은 하나, 역할은 필요한 만큼

기획부터 구현과 검증까지 맡기는 상황에서는 전체 목표와 승인 범위를 책임지는 담당이 필요합니다. 총괄은 일을 나누고 결과를 통합하며, 작거나 분리하기 어려운 일은 직접 수행합니다. 모든 요청에 다섯 명의 자문단이나 별도 리뷰어를 만드는 방식은 피합니다.

## 발견하고 수정한 다섯 문제

| 문제 | 적용한 규칙 |
|---|---|
| 직접 검토 요청과 자동 독립 리뷰가 충돌 | 직접 수행 요청을 해당 범위에서 우선하고 독립 검토로 표현하지 않음 |
| 모델 확인의 의미가 불명확 | 명시적 요청의 수락과 별도 실행 모델 확인을 구분 |
| 이미 승인한 Git 작업도 메뉴를 다시 요구 | 동일 대상·행위·범위의 승인을 재사용 |
| 작업트리 생성 실패 시 기존 폴더로 자동 이동 | 필요한 격리 조건 유지, 허용된 복구와 독립 작업 진행 |
| 폴더 이름으로 작업트리 소유권 추정 | 생성 기록·등록·현재 상태·정리 권한 확인, 불명확하면 보존 |

반복 승인과 정보 미노출만으로 발생하는 중단을 줄였지만, 파괴적 폐기의 정확한 `discard` 확인, 명시적 강제 푸시 요청, 브랜치 보호, 작업트리 동의, 세 차례 실패 후 접근법 상의 같은 의도된 안전장치는 유지합니다.

## 계획과 완료의 경계

기획·제안만 요청했다면 제안이 결과물입니다. 구현까지 승인된 요청은 계획 제출에서 멈추지 않고 요청 범위의 구현과 검증으로 이어집니다. 일부 단계가 막히면 독립적으로 가능한 일을 마치고, 미완료 부분과 이유를 분리해 전달합니다.

외부 스킬은 이름만 많이 모으기보다 목적·질문·승인·완료 규칙을 공통 지침과 맞추는 데 사용했습니다. 출처와 변경 범위는 [외부 자료 고지](../THIRD_PARTY_NOTICES.md)를 따릅니다. 앞으로의 개선은 실제 사용에서 관찰한 문제와 검증 근거를 중심으로 합니다.
